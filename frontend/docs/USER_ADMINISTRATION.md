# User administration

Accounts with `users.view` see the administrative list at `/users`. It uses `GET /api/v1/users` (`auth:sanctum`, active account, and `ListUsersRequest` authorization through `UserPolicy::viewAny`). Supported filters are search (string, max 100), account status (`active|suspended|pending`), global role slug (string, max 50), page size (integer 1–100, default 15), sort key (`id|name|email|created_at|last_login_at`), and direction (`asc|desc`). Laravel's paginator reads the conventional `page` query parameter. Results return a paginated `UserResource` and display account status, global roles, department, and a link to `/users/{id}`.

The detail route requires `users.view` in the frontend and loads `GET /api/v1/users/{id}`; backend `UserPolicy::view` allows the target themself or an actor with `users.view`. The success body is the full `UserResource`. Users with `users.update` may edit name, email, and time zone through `PUT /api/v1/users/{id}`. Backend validation allows optional name (string, max 255), email (unique, valid email, max 255), and nullable IANA timezone. The request can also accept role ID and account status, but backend authorization restricts both to System Admins and forbids self changes. The form does not expose either field. It surfaces 422 field validation failures and updates cached detail/auth data after success. Global role assignment is intentionally absent: although the update request accepts a role ID, this API has no roles-list endpoint from which the UI could safely resolve valid role IDs.

Account activation uses `POST /api/v1/users/{id}/activate` and requires `users.update`; deactivation uses `POST /api/v1/users/{id}/deactivate` and requires `users.delete`. Both run behind Sanctum and active-account middleware, return the updated `UserResource`, and take no request body. Laravel returns 403 for policy/business-rule denials (including self-deactivation, unauthorized System Admin changes, and the last active System Admin); 404 for an unknown ID; 401 for unauthenticated requests. Both require frontend confirmation. The UI prevents self status changes and mirrors System Admin restrictions where the target role is known; Laravel remains authoritative. Activation/deactivation mutations and their failures do not yet have dedicated component tests.

Dashboard and list interfaces have component tests using mocked auth/query data. API services have Axios-adapter tests for methods, paths, parameters, and data unwrapping. There are no dedicated tests for the detail route, update form, account action dialog, admin-list error/retry/filter/pagination behavior, or mutation cache invalidation. No live backend HTTP integration is claimed. Backend user API contracts and policies are documented in [`../../docs/api/USERS.md`](../../docs/api/USERS.md).
