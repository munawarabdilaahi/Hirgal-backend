# User administration

Accounts with `users.view` see the administrative list at `/users`. It uses `GET /api/v1/users` (`auth:sanctum`, active account, and `ListUsersRequest` authorization through `UserPolicy::viewAny`). Supported filters are search (string, max 100), account status (`active|suspended|pending`), global role slug (string, max 50), page size (integer 1–100, default 15), sort key (`id|name|email|created_at|last_login_at`), and direction (`asc|desc`). Laravel's paginator reads the conventional `page` query parameter. Results return a paginated `UserResource` and display account status, global roles, department, and a link to `/users/{id}`.

The detail route requires `users.view` in the frontend and loads `GET /api/v1/users/{id}`; backend `UserPolicy::view` allows the target themself or an actor with `users.view`. The frontend intentionally keeps `/users/:userId` administrative-only (decision B): personal account data/editing already belongs on `/profile`, while this screen includes account status and global-role details. Keeping the screens separate avoids duplicating the personal-account experience and prevents self-view from revealing administrative fields. The success body is the full `UserResource`. Users with `users.update` may edit name, email, and time zone through `PUT /api/v1/users/{id}`. Backend validation allows optional name (string, max 255), email (unique, valid email, max 255), and nullable IANA timezone. The request can also accept role ID and account status, but backend authorization restricts both to System Admins and forbids self changes. The form does not expose either field. It surfaces 422 field validation failures and updates cached detail/auth data after success. Global role assignment is intentionally absent: although the update request accepts a role ID, this API has no roles-list endpoint from which the UI could safely resolve valid role IDs.

Account activation uses `POST /api/v1/users/{id}/activate` and requires `users.update`; deactivation uses `POST /api/v1/users/{id}/deactivate` and requires `users.delete`. Both run behind Sanctum and active-account middleware, return the updated `UserResource`, and take no request body. Laravel returns 403 for policy/business-rule denials (including self-deactivation, unauthorized System Admin changes, and the last active System Admin); 404 for an unknown ID; 401 for unauthenticated requests. Both require frontend confirmation. The UI prevents self status changes and mirrors System Admin restrictions where the target role is known; Laravel remains authoritative. Activation/deactivation mutations and their failures do not yet have dedicated component tests.

Dashboard, list, and detail interfaces use component tests with mocked API responses and a real test `QueryClient`. Detail tests cover loading, success, 403/404/500 reads, retry, route denial, self-view denial, restricted update/action controls, name/email validation, backend email/timezone 422s, 403/404 updates, pending/duplicate update handling, update cache write/list invalidation, and preservation of cached data on failure. Account action tests cover cancel, activation, deactivation confirmation, duplicate prevention, status rendering, detail/list/directory invalidation, backend denial for a last-active System Admin, and 403/404/500 failures. Activation/deactivation endpoints accept no body, so a 422 action validation case is not applicable to this backend contract. Admin-list error feedback is tested; its search/filter/pagination interaction is less extensively covered than the directory. No live backend HTTP integration is claimed. Backend user API contracts and policies are documented in [`../../docs/api/USERS.md`](../../docs/api/USERS.md).

### Self-view route decision

`/users/:userId` remains administrative-only and requires `users.view`. Although Laravel permits self-view from `GET /users/{id}`, personal account details and edits already belong to `/profile`. The detail resource includes administrative status and global-role fields; keeping self-view there would duplicate the profile experience and require additional per-field restrictions. A test confirms that a user without `users.view`, including the target user themself, receives the access-denied screen without a details request.
